# Copilot catalog enrichment design

## Purpose

Extend Library Finder's AST catalog with concise, durable semantic explanations generated by the user's signed-in Microsoft 365 Copilot account. These explanations make otherwise opaque utility methods understandable to plain-language search and to Laya's later ranking pass.

## Scope and boundaries

- The existing AST scanner remains the source of truth for method identity, source location, signatures, visibility, and static facts. It does not execute or import library code.
- `catalog` sends every discovered method during its first enrichment run, including private methods. On later runs it sends only methods that are new, changed, or previously not enriched.
- Source snippets are sent to Microsoft 365 Copilot through a local, dedicated Edge profile controlled by Playwright, following the reusable approach in `m365-quick-hub`.
- Copilot is used only for analysis questions. The integration creates one dedicated catalog conversation and deletes that conversation after the catalog run completes; it must not modify files, settings, or unrelated Copilot chats.
- The project must not access the current user's normal browser profile, credentials, `.env` files, or the read-only automation repository.

## Architecture

Introduce a small Copilot client with three responsibilities: launch or attach to a dedicated Edge instance through a localhost CDP port, open the Microsoft 365 Copilot chat page, and submit/read one question at a time using the established typed-input and final-answer selectors. Browser-session data remains in a gitignored project-local profile directory so its sign-in can persist between catalog executions.

The catalog pipeline is:

1. AST scan the configured source directory as today.
2. Match each scanned method against the prior catalog by its stable key: normalized relative source path plus qualified method name.
3. Calculate a method content fingerprint from its AST-derived semantic inputs: signature, decorators, docstring, imports, inferred effects, and exact bounded source segment.
4. Retain the prior enrichment only when its fingerprint is equal and it has a successful enrichment status.
5. For all other methods, ask Copilot for a structured explanation and store its response with the new fingerprint.
6. Remove records for methods no longer present in the scan, then write the catalog atomically.

## Prompt and stored response

The client submits a bounded method snippet plus AST metadata and asks Copilot to return strict JSON with: `summary`, `purpose`, `inputs`, `outputs`, `side_effects`, `automation_context`, `keywords`, and `caveats`. The prompt tells Copilot to distinguish source evidence from inference, not invent APIs, and avoid suggesting code execution.

The resulting catalog record stores the parsed enrichment object, its status, the method fingerprint used to create it, and a timestamp. The original AST fields are never overwritten. A malformed or non-JSON reply is retained only as an error status and raw diagnostic-safe message; it must not be treated as semantic content.

## CLI behavior

`library-finder catalog` performs incremental enrichment by default. Its summary shows scanned, reused, enriched, failed, and skipped counts. It provides a clear prompt to run the local Copilot login/start command if the dedicated browser profile has no active Microsoft 365 session.

Cataloging does not fail wholesale when Copilot is unavailable, a single request times out, or a response is invalid. It writes AST records, preserves valid unchanged enrichments, marks affected methods as pending/error, and exits nonzero only with an explicit strict option. A subsequent catalog retries pending/error methods.

`find` adds successful Copilot fields to deterministic candidate text and to the bounded candidate metadata supplied to Laya. It labels records with missing or failed semantic enrichment rather than presenting generated meaning as an AST fact.

## Security and operational behavior

Cataloging submits internal source snippets to Microsoft 365 Copilot under the user's signed-in organization account. The CLI must print that disclosure before its first submission in a run. The user is responsible for confirming this use is allowed by company policy.

The CDP server listens on localhost only. While the dedicated browser is open, local processes can control that browser profile; the CLI documents this and closes its Playwright connection and opened tab in `finally` blocks. On normal completion, failure, or cancellation after a conversation is created, a `finally` cleanup attempts to delete only that catalog conversation, then reports if deletion could not be confirmed. The persistent browser profile retains only sign-in state, not the catalog conversation. It never prints user prompts, response bodies, browser cookies, credentials, or session data in logs.

## Verification

Unit tests use a fake Copilot client and cover first-run all-method enrichment, unchanged-result reuse, changed/new-method requests, removed-method pruning, a failed method continuing the run, retrying a prior failed method, JSON validation, prompt size limits, deterministic/Laya candidate enrichment, and conversation deletion on both success and failure. Browser integration is opt-in and never runs against the authenticated Copilot account in automated tests.
